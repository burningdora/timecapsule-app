# ADR-0006. Фоновые задачи через SNS, SQS и Lambda

* Статус: принято
* Дата: 2026-11-23
* Контекст: Lab 7, часть 2 (TimeCapsule)

## Контекст

В версии для ЛР5–ЛР6 приложение делало всю работу прямо в HTTP-запросе:

* `POST /seal` «отправлял письмо» синхронно (в учебной версии — задержка 5 секунд)
  и только потом отвечал пользователю;
* открытие капсул (`UPDATE capsules ... WHERE open_at <= now()`) выполнялось при
  каждом заходе на главную страницу, то есть только когда кто-то откроет сайт.

Замеры до изменений: `POST /seal` — **5,03 с** (DevTools, `Time` запроса), при этом
пользователь ждёт почтовый сервер. Капсула, открывшаяся ночью, оставалась
запечатанной до первого посетителя.

Требования задания: убрать медленную работу из запроса, открывать капсулы по
расписанию, не терять сообщения при сбоях и не создавать дублей уведомлений.

## Решение

1. **События вместо прямых вызовов.** Приложение публикует `capsule.sealed` в тему
   SNS `timecapsule-dev-events` и сразу отвечает. Тема связана с очередью
   `timecapsule-dev-mail`, из которой сообщения забирает Lambda `timecapsule-dev-mailer`.
2. **Фильтры на подписках.** Очередь получает только `capsule.sealed`, e-mail —
   только `capsule.opened` с `count > 0`. Фильтрация выполняется в SNS, лишние
   вызовы Lambda не тратятся.
3. **Расписание вместо запроса пользователя.** EventBridge Scheduler раз в минуту
   вызывает `timecapsule-dev-opener`; функция открывает все созревшие капсулы и
   возвращает событие `capsule.opened`, которое уходит в тему асинхронным
   назначением «при успехе».
4. **Идемпотентность на уровне БД.** `notifications` имеет ограничение
   `unique (capsule_id, kind)`, вставка идёт с `ON CONFLICT DO NOTHING`.
   Повторная доставка сообщения не создаёт второе уведомление.
5. **Защита от «плохих» сообщений.** DLQ `timecapsule-dev-mail-dlq` с
   `maxReceiveCount = 3`, батч 1 (одно плохое сообщение не блокирует остальные),
   `MaximumConcurrency = 2`, `VisibilityTimeout = 120 с` (больше таймаута функции).

## Последствия

* Время ответа `POST /seal` — **40–102 мс** вместо 5 с: запрос больше не зависит от
  почтового сервера.
* Капсулы открываются без посетителей сайта, с точностью до минуты.
* Доставка at-least-once: без ограничения в БД были бы дубли, поэтому идемпотентность
  обязательна и проверена тестом (4 доставки → 1 строка).
* Появились новые точки наблюдения: метрики очереди (в т.ч. «в полёте» и возраст
  старейшего сообщения), журналы двух функций, счётчик сообщений в DLQ.
* Открытие капсулы происходит не мгновенно, а в течение минуты после `open_at`.
* Функции в VPC: нужен доступ к RDS по 5432 из `timecapsule-dev-lambda-sg`, а для
  холодного старта — ENI в приватных подсетях.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Оставить отправку в запросе, но с таймаутом | запрос всё равно ждёт почтовый сервер и падает при его недоступности |
| Приложение пишет сразу в SQS | теряется возможность отдать одно событие нескольким подписчикам (очередь + письмо), фильтры SNS удобнее |
| SNS → Lambda напрямую, без очереди | нет буфера при всплесках и нет DLQ на уровне очереди; при ошибке сообщение теряется после ретраев |
| Step Functions для открытия капсул | избыточно для одной операции «обновить строки и отправить событие», дороже и сложнее |
| Открывать капсулы по cron на EC2 | нет гарантии запуска, нужен свой планировщик и своя обработка ошибок |
| Резервированная конкурентность = 1 | в учебном аккаунте квота 10, минимум незарезервированных — 10, поэтому используется `MaximumConcurrency` у триггера SQS |

## Проверка

* `POST /seal`: 5,03 с (inline) → 40–102 мс (sns) — скриншоты панели Network.
* Капсула 34: `open_at` 14:19:15, `opened_at` 14:19:53 — открыта расписанием.
* Письмо `capsule.opened` получено на e-mail (конверт с `responsePayload`).
* Сбой пароля БД: 2 сообщения, 3 неудачных приёма, 2 сообщения в DLQ; после
  исправления redrive → по одной записи `sealed` на капсулу (35, 36).
